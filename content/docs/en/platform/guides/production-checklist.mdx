---
title: Production Checklist
description: Verify your Nexus Signal integration is ready before switching to Production keys and routing live traffic.
---

Use this checklist before routing live user traffic to Production. Work through each section in order.

---

## Keys & environments

- [ ] Production secret key (`sk_prd_…`) stored in a secrets manager (e.g. AWS Secrets Manager, Vault, Railway secrets) — **never committed to git**
- [ ] Staging environment tested end-to-end with `sk_stg_…` and real provider credentials
- [ ] Public key (`pk_prd_…`) stored in frontend environment variables only — never exposed in backend services

---

## Providers

- [ ] All required channel providers connected under the Production environment
- [ ] **Test connection** button passed for each provider
- [ ] Weight splits configured correctly if using multiple providers per channel layer
- [ ] Provider unit costs entered for accurate [cost analytics](/docs/platform/features/cost-analytics)
- [ ] Monthly budget cap configured and alert email address verified

---

## Workflows & templates

- [ ] All templates promoted to **Production Active** (not Draft or Archived)
- [ ] All workflows set to **Active** in the Production environment
- [ ] Failover chains tested — at least one secondary provider per critical channel
- [ ] Delivery windows configured for user-facing marketing and digest sends
- [ ] Topics assigned to appropriate workflows and preference matrix tested end-to-end
- [ ] Smart Send-Time enabled on campaigns where applicable

---

## SDK & backend integration

- [ ] HMAC signature generated **server-side** per subscriber session — never computed in the browser
- [ ] Subscriber `externalId` values match your authentication system's user IDs exactly
- [ ] Node SDK error handling in place — check `result.ok` before using `result.data`
- [ ] Idempotency keys used on trigger calls that may retry on network failure
- [ ] Trigger payloads validated for correct `workflowName`, `recipients`, and `data` shape before sending

---

## Compliance & ops

- [ ] GDPR subscriber purge process documented — use `DELETE /v1/subscribers/:id` to erase profile, logs, and Redis state
- [ ] GDPR export endpoint tested — `GET /v1/subscribers/:id/export` returns complete data bundle
- [ ] Team roles assigned (Owner, Admin, Developer, Marketer) — no shared credentials
- [ ] MFA enabled for all Owner and Admin accounts
- [ ] Audit log retention and on-call monitoring plan defined

---

## Billing

- [ ] Plan tier matches expected monthly trigger volume
- [ ] Overage behaviour confirmed (soft cap with alert or hard stop)
- [ ] Stripe billing portal access confirmed for account Owners

---

## Go-live procedure

1. Switch the dashboard environment selector to **Production**
2. Deploy your backend with `sk_prd_…` and `pk_prd_…` environment variables
3. Send a canary trigger to an internal team subscriber first
4. Monitor **Audit Logs** and the **Overview** dashboard during the first hour
5. Confirm delivery success rate is above expected threshold before removing canary limits

<Callout type="warn">
  Development Sandbox mode does **not** carry over to Production. Every trigger in Production sends
  through real providers and incurs provider charges. Test thoroughly in Staging before switching.
</Callout>
